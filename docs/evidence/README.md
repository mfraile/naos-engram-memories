# Evidence records and their limits

Every file in this directory is a retained validation receipt. This page states
exactly what those receipts do and do not attest, so a reader does not infer more
from them than the runs actually established.

## They are not reproducible from this published tree

This repository was published from a fresh, rewritten history. The evidence files
were produced before that rewrite, so they cannot be re-derived from any commit
present here:

- 19 of the 20 records carry **no** source-commit or tree reference at all.
- `v1.20.0-windows-amd64.json` is the only record with provenance fields, and its
  `source_commit` (`f8b42a63…`) does not exist in this history. `git cat-file -t`
  on it fails.

Treat each record as a dated statement by its author about a run on a specific
machine, not as an artifact you can independently reproduce from this tree. New
receipts generated by `tools/validate_installed_runtime.py` on this history do
carry a resolvable `source_commit`, `source_git_tree`, and `package_input_sha256`.

## Toolkit version drift

The receipts were taken at different toolkit versions, which matters when a
receipt is cited as the basis for a platform promotion:

| Record | Toolkit version at capture |
| --- | --- |
| `v1.20.0-ubuntu-amd64-runtime.json` | `0.1.0` |
| `v1.20.0-windows-amd64.json` | `1.0.0` |
| `v1.20.0-darwin-arm64.json` | not recorded — this is provider evidence for the macOS ARM64 asset, not toolkit evidence |
| `v0.1.0-installed-runtime-darwin-arm64.json` | `0.1.0` |

So `linux_amd64: supported` in
[`config/release-support.json`](../../config/release-support.json) rests on a run
recorded at toolkit `0.1.0`. The provider asset and its checksum are unchanged
since, and the toolkit-side runtime path has since been re-validated on Linux
x86-64 at `1.0.1`, but the original receipt was not re-taken.

## Windows AMD64 is an owner promotion, not a clean-tree attestation

`v1.20.0-windows-amd64.json` records `disposition:
candidate_passed_not_release_attestation` and `source_worktree_dirty: true`, and
its own limitations say release promotion "remains a separate decision". The
manifest nevertheless marks `windows_amd64` as `supported`. That is a deliberate
owner promotion and is now labelled as such in `release-support.json`
(`promotion`), rather than being presented as something the receipt itself
established.

## Open gap: non-ASCII MCP stdio on Windows

Not a defect with a known reproduction — an untested path, recorded so it is not
mistaken for a covered one.

On Windows the managed chain is `engram-mcp-wrapper.cmd` → `powershell.exe`
(Windows PowerShell 5.1, not `pwsh`) → `engram.exe`. Windows PowerShell 5.1
re-encodes a native command's stdout through `[Console]::OutputEncoding`, which
defaults to the console's OEM code page, and the wrapper starts the provider with
`LANG=C`. MCP is newline-delimited JSON-RPC over stdio.

`v1.20.0-windows-amd64.json` exercises `initialize`, `tools/list`, and
`mem_current_project`, all of which carry ASCII-only payloads in that lane. A
round trip containing non-ASCII memory content (accented or CJK text) has
therefore **not** been validated on Windows. The mechanism is well documented and
the failure is plausible, but it has not been observed here and must not be
reported as either confirmed or excluded. Closing it requires a Windows host and
a receipt that asserts byte-exact non-ASCII content.

## Scope shared by all runtime receipts

- Synthetic only: no live memory database, real client configuration, cloud
  transport, or production project.
- They validate the provider and the installed stdio wrapper, never a named GUI
  or coding-agent host. Host acceptance is gated separately in
  [`config/mcp-host-observations.v1.json`](../../config/mcp-host-observations.v1.json).
- External provider adoption runs the selected binary's version command, so its
  network behaviour is reported as `not_observed`, never as "offline".
